# Lessons learned (and the rule each one became)

Collected while running this workflow on ferrocore (a Rust 5G core built by agents,
November 2026). Each entry: what happened, the rule or default that now prevents it, and
where it is encoded in the kit.

| # | What happened | Rule / default | Where |
|---|---|---|---|
| 1 | First spec drafts had 100-170 requirements. The critic never converged: each round raised new issues, the tests and code built on them bloated. | **Proportionality budget** (~15-45 requirements, `requirements.budget`); the author decides project-internal choices under *Decisions* and uses the clarification marker only for genuine source ambiguity; **convergence rounds** (later critic rounds only re-check earlier issues and report new *blocking* ones); a **product-owner resolution** step (decide, cut scope to the roadmap entry, defer to named future features), up to 2 passes, then a blocking-only final check. | spec-author/spec-critic/product-owner roles; pipeline Critic stage; constitution Article 2; `sdd spec-info` budget flag |
| 2 | A product-owner rejection ended the run with nothing to do but restart. | A rejection triggers **one spec-author fix pass and a re-review**, not a dead stop. | pipeline Approve stage |
| 3 | The marker count included the template's HTML comment and a prose mention of "[NEEDS CLARIFICATION", so approval was blocked by phantom questions. | Counting ignores HTML comments, fenced code, inline code spans and prose mentions; agents never count by eye. | `sdd markers`, `sdd spec-info`; integrator role |
| 4 | Two features specified in parallel defined the same requirement id; `trace --check` caught the duplicate only at merge time. | Requirement ids are **global**; each feature owns an id block `R<NNN*block_size>..` printed by `sdd new-feature`; `trace --check` fails on duplicates. | `requirements.block_size`, `sdd new-feature`, `sdd trace --check`, spec template D-1 |
| 5 | Tests-first with implementers forbidden from editing tests deadlocked when a test or snapshot was wrong: the implementer could not fix it and the test-author was not in the loop. | A **test-arbiter** step (test-author role) after 2 consecutive failing test gates decides whether the test or the code is wrong against the spec, fixes the wrong side minimally and records it in design.md "Test amendments". | pipeline gate loop; test-author role; constitution Article 4 |
| 6 | Branch switching in one checkout to run several features serialised everything and broke running agents; a union merge of a *source* file produced a main that compiled and was wrong, and had to be reverted. | Each feature runs in its **own worktree** (`.wt/<FID>`); merge `main` **into** the feature branch first and run gates there, then merge into main conflict-free. Conflicts are resolved **semantically by an agent**; only additive **manifests** may be union-merged (`sdd union-merge` refuses anything else). | `args.root`, Setup stage, `sdd union-merge`, integrator and implementer roles, PLAYBOOK §3 |
| 7 | A read-only verifier ran `git checkout -- . && git clean -fd` in a worktree another agent was editing, destroying its work. | **No destructive git commands in shared trees** (`checkout -- <path>`, `restore`, `clean`, `reset --hard`, `stash`), enforced by the bash-guard hook and the settings deny list for every role including the orchestrator; read-only roles experiment in a **detached throwaway worktree**. | `sdd hook bash-guard`, `.claude/settings.json` deny list, verifier role, CTX in the pipeline, constitution Article 12 |
| 8 | Full gate runs exceeded an agent's 10-minute shell limit; agents reported the partial log as a result. | Full gates run **detached** with an exit marker (`GATES_EXIT=<n>`); agents poll (`sdd gates --wait`) and never report a run without the marker. Keep gates fast: budgeted fuzzing, only changed targets, optimised test profile for heavy property tests. | `sdd gates --detached/--wait`, gates skill, integrator role |
| 9 | Agents died on outages and usage limits; a dead agent produced a null result, the script ran on with garbage, and the run could not be resumed consistently. | The pipeline **retries an agent once** (including agents that end without their structured output), then **stops issuing calls** and ends as `paused`; the run is resumed from its journal with the same args. Model choices of completed stages must not change on resume (cache keys), so tier changes apply **from a named phase onward** (`modelsFromPhase`, `modelsBefore`). | `agentR()` in the pipeline, `finish()`, PLAYBOOK §5 |
| 10 | Many parallel runs on the strongest model hit the usage limit; an alias (`fable`) silently resolved to a newer, pricier model. | **Model tiering by role**: mechanical / mid / strong / top (see PLAYBOOK §7); **explicit model ids** in config, never aliases; ids in `sdd.config.json`, not in the script. | `models` in config, `tierFor()` in the pipeline, config validation |
| 11 | Security fixes were incomplete twice (a cap that still allowed 64 KiB per entry; a redaction that left the value unzeroized). | Security-sensitive features need an **orchestrator/human sign-off**; the orchestrator demands cheap hardening fixes before merge and **independently re-verifies fixes twice**. | pipeline fix-checks (x2 when security-sensitive), product-owner role, review.md §4, PLAYBOOK §8 |
| 12 | An agent re-implemented a YAML parser just to zeroize buffers holding test data. | A **project threat-model statement** in config and CLAUDE.md says what is untrusted and what is not; reviewers and planners apply it and do not demand protections it rules out. | `project.threat_model`, security-reviewer and architect-planner roles, constitution Articles 3 and 10 |
| 13 | Build directories and worktrees on `/tmp` (RAM tmpfs) vanished on a crash; per-worktree build dirs reached 130 GB; a full host disk crashed the VM twice; a Windows update restarted WSL mid-run. | **Machine hygiene**: never put build dirs or worktrees on a RAM tmpfs; cap parallel build jobs per worktree; delete build output after merging; watch host disk; disable OS auto-updates during long runs. | DISK RULE in the pipeline CTX, `pipeline.max_build_jobs`, `paths.build_dirs`, PLAYBOOK §0 and §11 |
| 14 | Hooks that protect the normative source, constitution, agent config and vectors also blocked the orchestrator from patching the pipeline script that lived under `.claude/`; the live copy drifted to an untracked directory. | A documented **human override** (`SDD_ALLOW_PROTECTED=1`) and the live pipeline script in a **tracked, unprotected `tools/` folder**. | `override_env`, `tools/sdd/pipeline/`, DEVELOPMENT §8 |
| 15 | A performance gate without a baseline measured nothing; a regression was accepted by loosening a threshold. | Performance gates need a **measured baseline**; a regression exception is an **explicit, recorded product-owner decision** in review.md, never a loosened threshold. | gate-fix prompt (`perf-exception-needed`), `perfException` in the summary, perf-reviewer and product-owner roles, constitution Article 8 |
| 16 | Agents received relayed user chat messages (for example a status question typed while a run was going) and treated them as new instructions: they abandoned their task, and two implementers built duplicate kits. | **Scope rule**: only the prompt assigns work; any other request seen in the context is reported in the summary, never acted on. Reason: an agent cannot tell a relayed message from its own assignment, and acting on it silently forks the work. | `strictScope` pipeline arg (on by default), SCOPE RULE text in `CTX` for every agent |
| 17 | Gate-runner agents that ended their turn killed the foreground gate process; the pipeline counted these incomplete runs as gate failures and spent fix rounds on code that was not broken. | Gates run **detached and keyed by HEAD** (`<logs_dir>/gates/<feature>-<tag>-<sha7>.log`, the tag carrying the round), the runner waits for the exit marker, an incomplete run (killed, no marker) is **re-run fresh** up to 3 times and never counts as a failed round. Reason: an infrastructure failure is not a verdict on the code. | `sdd gates --detached/--wait/--fresh`, `gateLoop()`, gates skill, PLAYBOOK §4 |
| 18 | Usage-capped calls returned an empty result with no error text, so a fallback keyed on "limit" in the error string never fired; caps also turned out to be weekly, not only per 5 hours. | The cap fallback triggers on **any failed result** (null, undefined, thrown), marks the pool exhausted for the rest of the run, retries on the cheapest equal-or-smarter point and pauses only when none exists. Reason: error strings are not a contract, and a weekly cap does not reset during a run. | `agentR()` in the pipeline, `pools` in the models table, PLAYBOOK §6 |
| 19 | A red check that trusted the trace tool reported the new tests as missing: the tool did not scan the tool directory where they lived, and teaching it that directory was itself a task of the same feature. | The red check **cross-checks the tags directly** in the files the test author added (`sdd trace --include`) instead of relying on the configured scan globs alone. Reason: a checker that is part of the change cannot be the only witness for it. | `sdd trace --include`, red-check prompt, `outsideScan` |
| 20 | Review findings and verifier verdicts were lost when a paused run was resumed, because they lived only in agent results that were not persisted. | Findings and verdicts are **written to review.md and committed** after Review and Verify, before the run goes on. Reason: anything not on disk does not survive a pause. | Review/Verify record calls in the pipeline, PLAYBOOK §5 |
| 21 | Interrupted workers (outage, usage cap, killed session) left uncommitted edits in their worktrees. | **Never discard them automatically**: Setup stops (`blocked-setup`) and reports them; a person or an implementer commits or finishes them. Reason: the edits may be the only copy of hours of work, and destructive git commands are what destroyed work before (lesson 7). | Setup dirty-tree check, bash-guard, PLAYBOOK §5 |
| 22 | Dominated model/effort points (more cost for no more intelligence) were used, and downgrading a model after a failure produced more retries than it saved. | Use only **frontier points**; the level's intelligence floor is hard and escalation only goes up, never down. Reason: a failed attempt plus its retry costs more than the stronger model would have. | formula router, `sdd routing table`, monotonic retries (PLAYBOOK §7) |
| 23 | A red check reported all 52 `must` requirements of a feature untested: the trace tool did not scan the tooling directory that held the tests at all, and cross-checking only the files the test author listed (lesson 19) does not catch tests it did not list. | With `redCheckTags` the red check also searches the **whole repository** for Verifies tags with the configured tag syntax (`trace.verifies_keywords` + `requirements.id_regex`), counting every id of a multi-id or multi-line list; a requirement is untested only if neither the trace tool nor the search finds a test. Reason: a scan scope is configuration, and configuration can be wrong. | `redCheckTags` / `pipeline.red_check_tags`, red-check prompt, `tagOnly`, `outsideScan` |
| 24 | Review findings were lost again: a run restarted with stages from Verify (a new run, not a journal replay) had nothing to feed them back from, because the review record was prose; verdicts written only after the fixes were lost when the fix stage paused. | With `persistFindings`, review.md §3 carries a **machine-readable findings block** (id, reviewer, severity, location, claim, votes, outcome), verdicts are committed right after the votes, and a run started from `verify` reloads the block; refuted or fixed findings are not verified again. Reason: a record only a person can read cannot resume a run. | `persistFindings` / `pipeline.persist_findings`, review findings and verify record calls, `load persisted findings`, PLAYBOOK §5 |
| 25 | A build-cache measurement (cold workspace builds) ran while another feature's coverage run was going; the 16 GB host ran out of memory, the OOM killer took a test process and the session froze. | **One heavy build or test job at a time** on a small host (coverage, mutation, full builds, full gates, cache measurements); measure build caches only on an idle host; run mutation testing without the compiler-cache wrapper; expect cross-worktree cache hits mainly for registry dependencies. Reason: concurrent cold builds exhaust memory, and a cache does not make a build lighter. | PLAYBOOK §14, ADAPTING §9, `pipeline.max_build_jobs`, `pipeline.max_parallel_features` |
| 26 | Runs paused on a usage limit while the owner was away stayed paused for hours after the limit had reset: the orchestrator acts only on notifications, and nothing notified it. | After a pause on a usage limit, **schedule a one-shot wake-up at the reset time** that tells the orchestrator to resume the paused runs with the same args, and record the paused runs and their args where the orchestrator keeps its state. Reason: an event-driven orchestrator needs an event to resume. | PLAYBOOK §14, `paused` status and its `nextAction` |
| 27 | A new spec section (procedure step tables) was first required only in specs that cited a procedure, so finished specs had no section at all; nobody could tell "never checked" from "checked, none applies", and a forgotten procedure looked the same as an irrelevant one. | With `trace.procedure_steps.enabled` **every checked spec carries an explicit entry**: step tables, an exemption line per procedure with a reason, or one feature-wide `No step table: <reason>`; merged specs are retrofitted when the option is turned on, most with that one line. Reason: an absent section is not evidence that anyone looked. | `trace --check` (procedure-step entry), spec template, PLAYBOOK §15 migration note |
| 28 | A mutation-testing run took a 16 GB host down, init system and unrelated user services included: some mutants turn loops into runaway allocators, and with 3 mutation jobs of 8 test threads each every runaway test process reached about 2.5 GB within seconds, far faster than the 20 s test timeout could stop it. | **Cap each test process, limit parallelism, queue heavy jobs, guard the host**: `sdd check mutation` runs 2 jobs with 3 test threads each and caps each test process's address space (`ulimit -v`, 2 GiB) through a runner wrapper (for Rust the cargo target runner, so the compiler is not capped), so a runaway mutant fails alone and counts as caught; if the unmutated baseline fails only because of the cap, raise it, never remove it. Coverage and mutation run under a host-wide `flock` lock shared by every pipeline; an optional memory guard kills the largest test binary below a MemAvailable floor (1.5 GiB) and logs it. Survivors of a run that excluded slow end-to-end tests are re-run with them before they count as test gaps. Reason: a timeout bounds time, not memory, and the kernel's OOM killer does not know which process is the test. | `quality.mutation.jobs` / `test_threads` / `memory_limit_mib` / `env`, `quality.heavy_lock`, `tools/sdd/scripts/{memcap-runner.sh,heavy-lock.sh,memguard.py}`, PLAYBOOK §14, ADAPTING §6, test-adequacy-reviewer |
| 29 | A long mutation series held the host-wide heavy-job lock one package at a time in a loop; follow-up fixes of another feature waited four hours behind it, because `flock` is not fair: the loop re-took the lock the moment it released it. | The heavy-job lock is a **first-come-first-served ticket queue** (`<lock>.queue/`): only the oldest live ticket may wait on the lock, a returning loop step queues behind the jobs already waiting, dead and cancelled tickets are dropped. Lock each step of a long series separately and run short jobs first. Reason: a lock that is not fair turns "one heavy job at a time" into "the longest job forever". | `tools/sdd/scripts/heavy-lock.sh`, PLAYBOOK §14 |

## Principles behind the rules

1. **What must always happen is a hook, a gate or a tool, not a prompt.** Prompts drift;
   `sdd` commands and hooks do not.
2. **Checks are independent of the agent being checked.** Tests from a different agent;
   oracles from outside the codebase; reviewers with fresh context and read-only tools;
   skeptics that default to "refuted".
3. **Decide, do not debate.** Over-specification and unresolved questions are the main way a
   spec-driven loop stalls. Budgets, decisions and a product owner with authority keep it
   moving.
4. **Resilience is a feature of the orchestration, not of the agents.** Retries, pausing,
   journaled resume, exit markers and worktree isolation are what make unattended runs
   survive the real world.
